1 · ระบบประกอบด้วยอะไร

ส่วนประกอบของระบบ

QCheck เป็นเว็บแอปตัวเดียว เปิดได้ทั้งมือถือและ laptop โดยไม่ต้องติดตั้งจาก Store ทุกคำขอวิ่งผ่าน server ของ QCheck ซึ่งเป็นตัวเดียวที่คุยกับระบบกลาง TRW และฐานข้อมูล

2 · ผู้ใช้มีใคร ทำอะไร

ผู้ใช้ 9 บทบาท

พนักงานออฟฟิศ

เข้าด้วยรหัสพนักงาน + รหัสผ่านของระบบกลาง TRW บทบาทตั้งที่ระบบกลาง (role_prog ของ PRG003) QCheck อ่านมาใหม่ทุกครั้งที่ login

4 · ขั้นตอนการทำงานของโปรแกรม

โปรแกรมทำอะไรเบื้องหลัง

สิ่งที่เกิดใน server เมื่อผู้ใช้กดปุ่มในแต่ละขั้น ทั้ง 4 เรื่องนี้สร้างแล้วและมีเทสต์คุม

เข้าสู่ระบบ

สร้างแล้ว
  1. รับรหัสพนักงาน ถ้าขึ้นต้นด้วย F → ตรวจ PIN กับค่าที่ hash ไว้ในฐานข้อมูล (ไม่ส่งไประบบกลาง)
  2. รหัสอื่น → server เรียก API ระบบกลาง ตรวจรหัสผ่าน ต้องมีสิทธิ์ PRG003 และบทบาทที่ QCheck รู้จัก
  3. บันทึก/อัปเดตผู้ใช้และบทบาทลง users, user_roles (ถ้า DB ล่ม พนักงานออฟฟิศยังเข้าได้)
  4. สร้าง session cookie เข้ารหัส อายุ 12 ชม. และบันทึก audit
  5. ผู้ใช้หน้างานที่ใช้ PIN ชั่วคราว → พาไปตั้ง PIN ใหม่ก่อน

ผิดเกินกำหนดถูกล็อก · ระบบกลางล่มแสดง "ระบบไม่พร้อม" แยกจากรหัสผิด · ไม่บอกว่ารหัสไหนมีอยู่จริง

ทุกครั้งที่เปิดหน้าหรือกดปุ่ม

สร้างแล้ว
  1. อ่าน session cookie ถ้าไม่มีหรือหมดอายุ → กลับหน้า Login
  2. ผู้ใช้หน้างาน: อ่านสถานะและบทบาทจาก DB ใหม่ทุกครั้ง ปิดบัญชีแล้วใช้ไม่ได้ทันที
  3. เทียบบทบาทกับตารางสิทธิ์หน้า ไม่มีสิทธิ์ = ไม่พบหน้า และเมนูไม่แสดง
  4. ปุ่มบันทึกตรวจสิทธิ์ซ้ำอีกชั้นและบันทึก audit ค่าก่อน → หลัง

ซ่อนเมนูอย่างเดียวกันคนพิมพ์ URL ตรงไม่ได้ จึงตรวจที่ server ทุกครั้ง

เปิดแผน

สร้างแล้ว
  1. จัดรูปเลข Invoice / PO (ตัดช่องว่าง ตัวพิมพ์ใหญ่) แล้วค้นหัวเอกสารเดิม
  2. ไม่พบ → สร้างหัวเอกสาร กำหนดตรวจ = วันที่ Invoice + 90 วัน (ค่าจาก settings)
  3. มีแผนของเอกสาร + รุ่นนี้อยู่แล้ว → ปฏิเสธ (กันแผนซ้ำ)
  4. ออกเลข QP-YYMM-NNNN จากตัวนับรายเดือน แบบล็อกแถว
  5. คัดลอก % QC ปัจจุบัน คำนวณจำนวนที่ต้องตรวจ = ปัดขึ้น(ล็อต × 10%)
  6. บันทึกแผน + ประวัติสถานะ OPEN ทั้งหมดใน transaction เดียว

ทำใน transaction เดียว ถ้าขั้นไหนล้ม ทุกอย่างย้อนกลับ ไม่มีเลขแผนหายหรือหัวเอกสารค้าง

เปิดใบงาน (เรียกของเข้า)

สร้างแล้ว
  1. คำนวณ Need = เป้า 10% ของล็อต − ที่ตรวจไปแล้ว ถ้าครบเป้าแล้ว ใบนี้เป็น "เรียกเข้าแก้ไข" (Need 0)
  2. ตรวจจำนวนเรียกเข้า: ≥ Need และไม่เกินส่วนของล็อตที่ยังไม่เรียก
  3. 1 แผนเปิดได้ 1 ใบต่อวันเรียกเข้า
  4. ผู้รับผิดชอบ 2–5 คน ต้องเป็น QC Inspector ที่ยังใช้งานอยู่
  5. บันทึกใบงาน QP-…-1, -2, … ใบแรกเปลี่ยนแผนเป็น ASSIGNED และขึ้นใน "งานของฉัน" ทันที (ไม่ต้องกดรับ)
  6. เมื่อเรียกครบทั้งล็อตและตรวจครบเป้า ใบที่ไม่เคยตรวจเลยเปลี่ยนเป็น "ไม่สำเร็จ" อัตโนมัติ

กฎตามประชุม D (21 ต.ค.) ที่ QA Head ตัดสิน · ใบที่ไม่สำเร็จเก็บไว้เป็นประวัติ ไม่นำไปคำนวณ

สถานะแผน (ตามสเปก docs/03 §2.1)

สีเขียว = โค้ดเปลี่ยนเข้าสถานะนี้ได้แล้ว (เปิดแผน, มอบหมายเมื่อเปิดใบงานแรก, กลับเป็น OPEN เมื่อยกเลิกใบงานจนไม่เหลือ, ยกเลิกแผน) · เส้นประ = รอโมดูล Checklist, QA และ Report

สถานะใบงาน

ตอนนี้ยังไม่มีหน้า Checklist ใบงานจึงยังไม่ถูกส่ง (SUBMITTED) จากการตรวจจริง

6 · ยังต้องตัดสิน

เรื่องที่ยังรอคำตอบและกระทบภาพรวม

  • T1 / T2 นำ QA แกนหลักเข้า Phase 1 หรือไม่ และใช้ timeline แบบไหน
  • A16 แบรนด์ PUMA นำเข้าจาก OEM ด้วยหรือไม่ (กระทบกฎ 10%, AQL ตั้งต้น, Report, NCP)

  • A17 ตอนเปิดแผนแรกกรอกแค่ "จำนวน SKU" หรือรายการรุ่นทั้งหมดใน Invoice
  • ค่าจริงของตาราง AQL ยังรอไฟล์จาก QA · โมดูลที่ยังไม่สร้างทั้งหมดอ้างอิงตามสเปก อาจปรับหลังประชุมยืนยัน
