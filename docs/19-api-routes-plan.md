# 19 — แผนย้ายการเขียนข้อมูลจาก Server Actions ไปเป็น API routes (`app/api/...`)

> 26 ต.ค. 2026 · ผู้ใช้ขอให้โครงเหมือนโปรเจกต์ log-book (ทุกอย่างที่ต่อ DB อยู่ใน `app/api/<ฟีเจอร์>/<ย่อย>/route.ts`) และ OK แผนนี้ → **ครบทุกขั้น (0–7) แล้ว** (ทดสอบด้วยเทสต์, ยิงจริงทุก endpoint และลองในเบราว์เซอร์โหมดสาธิต — ดู §8; **ยังไม่ได้ลองกับ SQL Server/ระบบกลางจริง**) · ทำทีละขั้น หยุดรอผู้ใช้ confirm ก่อนทุกขั้น
> สำรองก่อนเริ่ม: `.local-backups/before-api-routes-2026-10-26/originals.tar.gz` (โปรเจกต์นี้ไม่มี git)
> ต่อมา 26 ต.ค. 2026: ผู้ใช้สั่งให้ย้ายหน้าเดิมที่อ่านผ่าน `lib/` ไปอ่านผ่าน `GET /api` **ทีละหน้า กด confirm ก่อนทุกหน้า** — ลำดับและความคืบหน้าอยู่ใน **§9** (ทำแล้ว: `/jobs`, `/history`, `/master`, `/plans`, `/home`)

## 1. หลักการ

1. **`lib/` ไม่แตะ** — route แต่ละตัวเป็นตัวห่อบาง ๆ ที่เรียก service เดิม (`openPlan`, `createMaster`, `changeOwnPin` …) กติกาธุรกิจ audit SQL และเทสต์เดิมใช้ต่อ
2. **ตัวช่วยกลาง `lib/api/`** เขียนครั้งเดียว: ตรวจ same-origin + session + สิทธิ์ตามหน้า, อ่าน body, ตอบ JSON, แปลง DB error
3. **ฟอร์มแก้น้อย** — ยังใช้ `<form action>` กับ `useActionState` (ผ่าน `useApiAction`) จึงได้ปุ่ม pending และการล้างช่องหลังตอบเหมือนเดิม; รูปแบบ state (`error` / `fieldErrors` / `at` …) คงเดิม ข้อความที่ผู้ใช้เห็นไม่เปลี่ยน
4. **หลังบันทึก** route ส่ง `redirectTo` ให้เบราว์เซอร์พาไปหน้าที่ action เดิมเคย `redirect()` ไป; ถ้าอยู่หน้าเดิมจะ `router.refresh()` (`revalidatePath` ใน route ไม่ล้าง router cache ฝั่งเบราว์เซอร์เอง)
5. **การอ่าน** หน้าที่ย้ายแล้ว (§9) ให้ client component อ่านผ่าน `GET /api/<ฟีเจอร์>` (`useApiRead`) ตามแบบ log-book — `page.tsx` เหลือแค่ด่านสิทธิ์ที่ server · หน้าที่ยังไม่ย้ายยังอ่านผ่าน `lib/` ตรง ๆ ใน server component (ไม่ยิง API ของตัวเอง) จนกว่าจะถึงคิว

## 2. สัญญา API

| เรื่อง | กติกา |
|---|---|
| Body เข้า | JSON (ฟอร์มส่งเป็น JSON — ช่องชื่อซ้ำเป็น array) หรือ form ธรรมดา (`urlencoded` / `multipart`) ก็อ่านได้ → ทดสอบด้วย Postman/curl ได้ body ที่อ่านไม่ออกถือเป็นช่องว่าง ให้กติกา "ต้องกรอก" ตอบเอง |
| Body ออก | JSON ที่มี `status` เสมอ: `done` / `error` / สถานะเฉพาะฟอร์ม (เช่น `duplicate`) — ตรงกับ state ที่หน้าจอเดิมใช้; `error` มี `message` ภาษาไทยพร้อมแสดง; อาจมี `redirectTo` (เฉพาะ path ในเว็บเรา) |
| Body ออกของ `GET` (อ่านข้อมูล) | ข้อมูลตรง ๆ ไม่ห่อ `status` (`apiData`) เหมือน log-book · ล้มเหลวใช้รูป `{ status: "error", message, redirectTo? }` เหมือนฝั่งเขียน ฝั่งเบราว์เซอร์แยกสำเร็จ/ล้มเหลวด้วย HTTP status (`readApi`) · `GET` ไม่ตรวจ same-origin (ไม่เปลี่ยนข้อมูล) แต่ตรวจ session และสิทธิ์ตามหน้าเหมือนกัน |
| Header ออก | `Cache-Control: private, no-store` + `Vary: Cookie` ทุกคำตอบ |
| ไม่ได้ล็อกอิน | `401` + `redirectTo: /login?next=…` (ไม่ redirect เอง) |
| ค้างเปลี่ยน PIN | `403` + `redirectTo: /change-password` (ยกเว้น endpoint เปลี่ยน PIN เอง) |
| ไม่มีสิทธิ์ตามหน้า | `403` (ใช้ตาราง `PAGE_ACCESS` ตัวเดียวกับเมนูและหน้า) |
| ส่งข้ามเว็บ | `403` สำหรับ POST/PUT/PATCH/DELETE ที่ไม่ใช่ same-origin (แทนการตรวจ CSRF ที่ Server Actions เคยทำให้) |
| ข้อมูลผิดที่แก้ได้ | `422` (เช่น PIN รูปแบบผิด) · ไม่พบ `404` · ล็อก `423` · ซ้ำ/สถานะเปลี่ยน `409` |
| DB ล่ม | `503` + ข้อความเดิมจาก `dbProblemMessages` (ไม่โชว์ error ดิบ) |
| บั๊กจริง | โยนต่อเป็น `500` (ไม่กลืน) |

## 4. ตัวช่วยกลาง `lib/api/`

| ไฟล์ | หน้าที่ |
|---|---|
| `guard.ts` | `guardApi(request, { page?, returnTo?, allowPasswordChange? })` → `{ user }` หรือ `{ response }` (ด่านแรกของทุก route) |
| `body.ts` | `readFields(request)` → `get` / `text` / `all` อ่านได้ทั้ง JSON และ form (ตัวแยกฟอร์มเดิมที่รับ `get(key)` ใช้ต่อได้เลย) |
| `response.ts` | `apiJson(body, status)` · `apiError(status, message, extra?)` · `apiData(body)` (คำตอบของ `GET`: ข้อมูลตรง ๆ) + header ไม่ cache |
| `db.ts` | `dbFailure(error, label)` ใน `catch` ของ route ที่แตะ DB: DB error → 503, อย่างอื่นโยนต่อ |
| `messages.ts` | ข้อความไทยกลาง (ไม่มีสิทธิ์ เซสชันหมด เครือข่ายล่ม ฯลฯ) |
| `call.ts` | `callApi(url, method, formData, failed)` ฝั่งเบราว์เซอร์: ส่งฟอร์มเป็น JSON, แยก `redirectTo` (ตัดที่ออกนอกเว็บทิ้ง) และ `refresh` ออกจาก state, ถ้าเครือข่ายล่ม/ตอบไม่ใช่ JSON ให้ใช้ error state ของหน้านั้น (ส่งฟอร์มที่ผู้ใช้พิมพ์ให้ด้วย จะได้เก็บค่าไว้) |
| `client.ts` | `useApiAction(url, initial, failed, method?)` แทน `useActionState(serverAction, initial)` · `useApiCall(url, failed)` สำหรับปุ่มที่ไม่ใช่ฟอร์ม (ช่องติ๊ก) — ทั้งคู่คง `pending` ไว้จนกว่าหน้าจะรีเฟรช/เปลี่ยนหน้าเสร็จ · `useApiRead<T>(url)` สำหรับหน้าที่อ่านข้อมูล → `{ data, loading, error, reload }`: ยิงตอน mount และเมื่อ `url` เปลี่ยนหรือสั่ง `reload()`, คงข้อมูลเดิมไว้ระหว่างโหลดใหม่, ยกเลิกคำขอที่ถูกคำขอใหม่แทนที่, 401 พาไปหน้า login ตาม `redirectTo` |
| `invalidate.ts` | `invalidateApiReads()` · `apiReadVersion` · `subscribeApiReads` — ตัวนับเวอร์ชัน "ข้อมูลที่อ่านมาเก่าแล้ว" ของแท็บเบราว์เซอร์: `useApiAction`/`useApiCall` เรียกตอนตอบ `done` (หรือ `refresh: true`) ก่อน `router.refresh()` แล้ว `useApiRead` ทุกตัวในหน้า (สมัครผ่าน `useSyncExternalStore`) ใส่เวอร์ชันในคีย์คำขอ จึงโหลดใหม่เอง — ฟอร์มไม่ต้องรู้ว่าหน้าอ่านอะไร · ข้อมูลเดิมค้างบนจอ (หรี่) ระหว่างโหลดเหมือนตอนเปลี่ยนตัวกรอง |
| `read.ts` | `readApi(url, { signal? })` ฝั่งเบราว์เซอร์: `GET` แล้วคืน `{ ok: true, data }` หรือ `{ ok: false, message, redirectTo }` ไม่ throw (เครือข่ายล่ม/ตอบไม่ใช่ JSON ใช้ข้อความกลางใน `messages.ts`, ตัด `redirectTo` ที่ออกนอกเว็บทิ้ง) + `settleRead`/`readView` ตรรกะ "คงข้อมูลเดิมไว้ระหว่างโหลดใหม่" ที่ `useApiRead` ใช้ (แยกไว้ให้เทสต์ได้) |
| `query.ts` | `readQuery(request)` ฝั่ง server: แอดเดรสของคำขอ → ออบเจ็กต์รูปเดียวกับ `searchParams` ของหน้า (ชื่อเดียว = string, ชื่อซ้ำ = array) เพื่อให้ route `GET` ใช้ parser ตัวเดียวกับหน้าที่มันแทน เช่น `parseHistoryQuery` |
| `lib/plans/api.ts` | ของกลางของ route แผน: `actorIdOf` (users.id สำหรับคอลัมน์ผู้ทำ), `planIdOf`, `revalidatePlan`, ข้อความ `CANCEL_MESSAGES` + `CANCEL_STATUS`, `NO_ACCOUNT` |

## 6. สิ่งที่ต่างจากเดิม / ความเสี่ยง

- **ฟอร์มต้องรอหน้า hydrate ก่อน** — Server Action เดิมส่งฟอร์มได้แม้ JavaScript ยังไม่ทำงาน; แบบ `fetch` ไม่ได้ (React กันไม่ให้ฟอร์มถูกส่งแบบเปล่า ๆ: ตัวฟอร์มมี `action="javascript:throw …"` จึงไม่ส่งและไม่มีรหัสผ่านต่อท้าย URL)
- **ตัดสินใจ login (ขั้น 6): ทาง A — รอ hydrate + กันกดเร็วเกินไป** เทียบกับทาง B (route รับ form POST ธรรมดาตอบ `303`, ส่งสถานะผ่าน URL) และทาง C (คง Server Action): JS ที่ต้องโหลดเพื่อ hydrate `/login` ~184 KB gzip (framework ~168 + หน้า ~16) ส่วนฉาก 3D ~279 KB โหลดทีหลังตอนเบราว์เซอร์ว่าง ไม่ขวางฟอร์ม (ค่าประมาณจากไฟล์ build ยังไม่ได้วัดบนมือถือจริง) · หลังขั้น 1–5 ทุกการเขียนในแอปต้องใช้ JS อยู่แล้ว ประโยชน์ของ login ที่ไม่ต้องใช้ JS จึงน้อย แต่ทาง B เพิ่มพื้นผิวเสี่ยงที่ endpoint ละเอียดอ่อนสุด
  - ปุ่มเข้าสู่ระบบ `disabled` + "กำลังเตรียม…" จนหน้าพร้อม (ปุ่มหลักที่ปิดกัน Enter ส่งก่อนเวลา) · ข้อความที่พิมพ์ระหว่างรอไม่หาย (React ไม่เขียนทับ `value` ตอน hydrate — ดู `initInput` ใน react-dom) · `<noscript>` บอกให้เปิด JavaScript · แก้คำอธิบายใน docs/07 §9 แล้ว
  - **ตัด Referer fallback ของ `next` ออก**: เดิมมีไว้ให้การส่งก่อน hydrate (ช่อง `next` ยังว่าง) ย้อนไปอ่าน `?next=` จากหน้าเดิม ตอนนี้ฟอร์มส่งได้หลัง hydrate เท่านั้น ช่อง `next` จึงมีค่าเสมอ
  - **สถานะใหม่ `unreachable`** (สร้างโดยฟอร์มเอง ไม่ใช่เซิร์ฟเวอร์): เครือข่ายหลุด/เซิร์ฟเวอร์รีสตาร์ท/ได้หน้า crash กลับมา → แสดง "เชื่อมต่อเซิร์ฟเวอร์ไม่สำเร็จ ลองใหม่อีกครั้ง" ในฟอร์มแทนหน้า error เต็มจอ (เก็บรหัสพนักงานที่พิมพ์ไว้) · `login/error.tsx` เหลือเป็นตาข่ายสุดท้ายตอนหน้า login พังตอน render
  - สถานะ HTTP: ผิด `401` · ช่องว่าง/รหัสผ่านยาวเกิน `422` · ล็อก/PIN ล็อก `423` · ปิดใช้งาน/ไม่มีสิทธิ์/ส่งข้ามเว็บ `403` · ระบบกลางล่ม `503` · `busy` (ยิงขนานเป็นสคริปต์) ตอบเหมือน "ผิด" ทุกประการ (`401`) ผู้โจมตีจึงแยกไม่ออก · สำเร็จตอบ `status: "success"` + `next` **ไม่ใช้ `redirectTo`** เพราะฟอร์มต้องเล่นอนิเมชันต้อนรับก่อนแล้ว `window.location.replace(next)` (โหลดทั้งหน้าเพื่อล้างข้อมูลผู้ใช้คนก่อนบนเครื่องส่วนกลาง) เหมือนเดิม
  - ขนาด body จำกัด 16 KB ที่ login (Server Action เดิมถูก Next จำกัด 1 MB ให้เอง) และ `readFields` มีเพดานเริ่มต้น 1 MB กับทุก route (ดู Content-Length ที่ประกาศ — proxy ยังต้องจำกัด chunked upload เอง)
  - `/api` ถูกเพิ่มใน `authOnlyPaths` กัน `?next=/api/...` กลายเป็นหน้าปลายทางหลัง login
- **เปลี่ยน PIN ตอนนี้จับ DB ล่มเป็นข้อความได้** (เดิม action ไม่ดัก ทำให้หน้าพัง) — เป็นการปรับปรุงเล็ก ๆ ที่มากับการย้าย
- **`id` ของผู้ใช้ย้ายจากช่องซ่อนในฟอร์มไปอยู่ใน path** (`/api/admin/users/[id]/…`) และรับเฉพาะ `[A-Za-z0-9_-]` ยาวไม่เกิน 40 ตัว ไม่ตรงตอบ `404` · `active` รับ `"1"` หรือ `"true"` เพื่อเปิด ค่าอื่นคือปิด (ค่าเริ่มต้นปลอดภัย)
- **ข้อมูลหลัก:** `slug` และ `id` ย้ายจากช่องซ่อนในฟอร์มไปอยู่ใน path (`/api/master/brands/3`) · ฟอร์มสร้าง/แก้ยังได้ค่าที่พิมพ์คืนเมื่อถูกปฏิเสธ (`values` + `at`) และเมื่อเครือข่ายล่มก็อ่านค่าที่พิมพ์กลับจากฟอร์มที่ส่ง (`failed(message, formData)`) · บันทึกสำเร็จตอบ `redirectTo: /master/<slug>?saved=<id>` เหมือน `redirect()` เดิม · `active` ตีความเหมือนผู้ใช้หน้างาน
- **แผน:** `planId` ย้ายจากช่องซ่อนไปอยู่ใน path · เปิดแผนซ้ำ Invoice/PO + Model (BR-01) ตอบ `409` พร้อม `status: "duplicate"`, `planId`, `planNo` (ฟอร์มยังโชว์ลิงก์ไปแผนเดิม) · ยกเลิกแผนถูกปฏิเสธ: ไม่พบ `404` · ต้องกรอกเหตุผล/ยาวเกิน `422` · สถานะเปลี่ยน/ยกเลิกไม่ได้ในสถานะนี้ `409` · มีผลตรวจแล้วต้องให้ Head `403` · Vendor ไม่มี/ปิดใช้งาน `422`, แผนถูกยกเลิก `409`
- **`GET /api/plans/lookup-doc`** ตอบ `{ status: "done", result: DocLookup }` (ห่อไว้เพื่อให้ทุกคำตอบมี `status`) · DB ล่มเป็น `503` แทน `{kind:"error"}` เดิม ฝั่งเบราว์เซอร์แปลงกลับเอง
- **ช่อง "รอของ"** แสดงค่าใหม่ทันทีที่ติ๊กและคงไว้จนหน้ารีเฟรชเสร็จ ถ้าเซิร์ฟเวอร์ปฏิเสธจะกลับเป็นค่าเดิมพร้อมข้อความ · ปุ่มในทุกฟอร์มยังถูกล็อกจนกว่าหน้าใหม่จะแสดง (ก่อนหน้านี้ขั้น 1–3 รีเฟรชแต่ไม่ล็อกปุ่ม)
- **ใบงาน:** `planId` และ `woId` ย้ายจากช่องซ่อนไปอยู่ใน path · ผู้ตรวจยังส่งเป็นช่อง `assignee1…assignee5` ตามลำดับช่อง (ตัวเลือกลากวางไม่เปลี่ยน) · ใบงานใน path เป็นตัวตัดสินว่าแก้ใบงานไหน (เหมือนเดิม) ส่วนแผนใน path ใช้เป็นที่กลับไปหลังล็อกอินและตรวจสิทธิ์ · เปิดใบงานสำเร็จตอบ `redirectTo: /plans/<id>?tab=work&opened=<woNo>`
- **คำตอบมี `refresh: true` ได้** (เพิ่มในขั้น 5): ใช้เมื่อถูกปฏิเสธเพราะข้อมูลที่หน้าแสดงอยู่เก่าไปแล้ว — กรณีเดียวตอนนี้คือเปิดใบงานแล้วพบว่ามีผู้ตรวจถูกปิดใช้งานระหว่างนั้น (`unavailable`) เบราว์เซอร์จะโหลดหน้าใหม่ให้รายชื่อตัดคนนั้นออก (Server Action เดิมทำสิ่งนี้ผ่าน `revalidatePath` ซึ่ง route ทำแทนไม่ได้)
- **ผู้ตรวจที่ถูกปิดใช้งาน:** เปิดใบงาน `422` + `unavailable` + `refresh` · เปลี่ยนผู้ตรวจ `422` (เหมือนเดิม ไม่รีเฟรชอัตโนมัติ) · ใบงานล็อก (ส่งแล้ว/ปิด/ยกเลิก/มีผลตรวจแล้ว) `409`
- **PIN ชั่วคราวอยู่ในคำตอบครั้งเดียว** (`no-store`) ไม่เข้า audit/log — มีเทสต์ยืนยันทุก route ที่ออก PIN
- **ใช้ DB ตัวเดียวกับของเดิม** ไม่มีการเปลี่ยน schema ใด ๆ ในแผนนี้
- **ออกจากระบบย้ายเป็น `/api/auth/logout`** ตรรกะเหมือนเดิมทุกอย่าง (ฟอร์ม POST ธรรมดา ตอบ `303` ไป `/login` แบบ relative ไม่ต้องใช้ JS) แก้ `authPolicy.logoutPath` (ปุ่ม `SignOutButton` อ่านจากที่นี่) · ไม่มี Server Action เหลืออยู่ในโปรเจกต์แล้ว
