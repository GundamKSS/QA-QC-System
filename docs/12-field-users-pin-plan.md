# ผู้ใช้หน้างาน (ไม่มีบัญชีระบบกลาง) + PIN — แผนก่อนลงมือ

> อัปเดตหลังซ่อม DB: เชื่อม SQL Server จริงได้แล้วด้วย TLS trust เฉพาะเครื่อง dev; รัน `008_users_schema_repair.sql` เติม 3 คอลัมน์ที่ขาดใน schema รุ่นเดิม และ Chrome อ่าน `/admin/users` จาก SQL store ผ่าน (LOCAL 0 คน) · ยังไม่รัน seed/ทดสอบเขียนผู้ใช้หรือ PIN และตั้ง `PIN_PEPPER` เฉพาะเครื่องพัฒนาแล้ว; ไม่มี `schema_migrations` จึงยังไม่ยืนยันประวัติ runner ทั้งชุด

> สถานะ: **แผน — ยังไม่เขียนโค้ด** · 19 ต.ค. 2026 · **DEC-12 กลับคำตัดสิน DEC-11 (ไม่ใช้ PIN) และแก้ DEC-09 บางส่วน**
> เหตุผล: พนักงานหน้างานที่ไม่ได้อยู่ในออฟฟิศ **ไม่มีบัญชีในระบบกลาง TRW** (ไม่มีรหัสพนักงาน/สิทธิ์ PRG003) แต่ต้องใช้ QCheck ตรวจงาน · ใช้ทั้งเครื่องส่วนกลางและมือถือส่วนตัว
> ตอนนี้ login ได้เฉพาะผู้ใช้ในออฟฟิศ (บัญชีระบบกลาง) — เอกสารนี้ออกแบบส่วนที่เพิ่ม ไม่รื้อของเดิม

## 0. ตัดสินใจแล้ว (19 ต.ค. 2026 — ใช้ค่าตั้งต้นทั้งหมดของ I1–I6)

| # | ผล |
|---|---|
| I1 | รหัสผู้ใช้หน้างาน `F` + ตัวเลข ≥ 4 หลัก (F0001) Admin ออกให้ |
| I2 | บทบาทหน้างาน: `QC_INSPECTOR`, `QA_INSPECTOR` เท่านั้น |
| I3 | PIN 6 หลัก |
| I4 | ปลดล็อก PIN: Admin + QC Head (ลูกทีมตัวเอง) |
| I5 | Admin สร้าง/ปิดบัญชี; QA Head แจ้งเมื่อมีคนออก |
| I6 | เข้าได้จากอินเทอร์เน็ตทั่วไป + จำกัดต่อ IP |

## 0b. ความคืบหน้า — ขั้น 2 ของ §4 ทำแล้ว (logic + migration, ยังไม่ต่อ login/UI)

182 tests ผ่าน · ไม่ต้องติดตั้งไลบรารีเพิ่ม
- `lib/config/auth.ts`: `pin` (6 หลัก, ผิด 5 ครั้ง) และ `local` (รูปแบบรหัส `F\d{4,}`, บทบาทที่อนุญาต)
- `lib/auth/pin.ts`: `pinFormatError` (ห้ามซ้ำ/เรียง), `createPinGuard` (ล็อกรายบัญชีแบบไม่หมดเวลา + จำกัดต่อ IP 30 ครั้ง/15 นาที), `hashPin`/`verifyPin` (HMAC ด้วย pepper แล้ว scrypt+salt)
- `lib/auth/local-users.ts`: `isLocalCode`, `checkLocalRoles` (ปฏิเสธ ADMIN/หัวหน้า/รหัสที่ไม่รู้จักพร้อมบอกเหตุผล)
- `db/003_local_users.sql`: `source = 'LOCAL'`, คอลัมน์ PIN, CHECK ว่ารหัส LOCAL ต้องเป็น `F####…` และ PIN มีได้เฉพาะ LOCAL — มี schema รุ่นเดิมใน DB จริงแล้ว; เติมคอลัมน์ที่ขาดด้วย 008 และตรวจการอ่านจริงผ่าน ส่วนการเขียน/PIN ยังไม่ทดสอบ
- `.env.example`: เพิ่ม `PIN_PEPPER` (≥ 32 ตัวอักษร, ต้องตั้งก่อนใช้ PIN; เปลี่ยนแล้ว PIN เก่าใช้ไม่ได้)
- **ต่างจากแผนเดิม:** ใช้ scrypt (ตัวเดียวกับ `password.ts`) แทน Argon2id เพราะ `engines` ของโปรเจกต์คือ Node ≥ 22.12 แต่ `crypto.argon2` มีตั้งแต่ Node 24.7 — รูปแบบ hash มีหัว `scrypt$…` จึงย้ายไป Argon2id ภายหลังได้
- **ที่ยังไม่ทำ:** เส้นทาง login LOCAL, ตรวจ `is_active` ทุกคำขอ, หน้า Admin, บังคับเปลี่ยน PIN, audit ใหม่ — รอฐานข้อมูลใช้งานได้

## 0c. ความคืบหน้า — ขั้น 3 ทำแล้ว (เส้นทาง login LOCAL ต่อเข้าโค้ดจริง)

190 tests ผ่าน (เพิ่ม 8 ตัวใน `local-auth.test.ts` ใช้ store จำลอง ไม่ต้องมี DB) · lint/typecheck ผ่าน · เปิดหน้า login ใน Chrome ได้ ป้ายช่องที่สองเป็น "รหัสผ่าน / PIN"
- `local-store.ts`: interface `LocalUserStore` + store หน่วยความจำ (ทดสอบ/ไม่มี DB) · `db/local-users.ts`: store SQL Server (อ่านรายชื่อจาก DB จริงผ่านแล้ว; การเขียน/PIN ยังไม่ทดสอบ)
- `local-auth.ts` → `authenticateLocal()`: รหัสรูป `F…` **ไม่ส่งไประบบกลางเลย**; รหัสที่ไม่มีจริงตรวจกับ dummy hash แล้วล้มแบบเดียวกับ PIN ผิด (กันเดารหัส) และถูกล็อกเหมือนบัญชีจริง; ผิด 5 ครั้ง → `pinLocked` และบันทึกลง `pin_locked_at` (ไม่หายเมื่อรีสตาร์ท); ตัวจำกัดต่อ IP **ไม่ถูกรีเซ็ตเมื่อ login สำเร็จ** (กันใช้บัญชีตัวเองเติมโควตา); บัญชีที่ถูกปิดจะบอกเมื่อใส่ PIN ถูกเท่านั้น; บทบาทกรองให้เหลือเฉพาะ QC/QA Inspector อีกชั้น
- `authenticate.ts`: ถ้ารหัสเป็น LOCAL และไม่ได้ตั้ง `PIN_PEPPER` → "ระบบไม่พร้อม" (ไม่ล้มทั้งแอป)
- `session.ts` เก็บ `src: LOCAL`; **`dal.ts` อ่านผู้ใช้ LOCAL จาก store ทุกคำขอ** → Admin ปิดบัญชีหรือเปลี่ยนบทบาทแล้วมีผลทันที (R5)
- `app/api/auth/login/route.ts` (เดิม `login/actions.ts`): ผู้ใช้ LOCAL ไม่ผ่าน `syncUserOnLogin`; audit ใหม่ `login.pin_failure`, `login.pin_lockout`, `login.pin_locked`
- UI: สถานะ `pinLocked` + ข้อความ "PIN ถูกล็อก… ติดต่อ Admin หรือหัวหน้า QC เพื่อปลดล็อก" (ไม่มีตัวนับเวลา)
- **ข้อจำกัดที่รู้:** (1) คำเตือน "เหลืออีก N ครั้ง" ยังไม่แสดงสำหรับ PIN เพราะข้อความเดิมเขียนว่า "ล็อก 15 นาที" ซึ่งไม่ตรงกับ PIN; (2) ยังไม่มีการบังคับเปลี่ยน PIN ครั้งแรก (`mustChangePassword` = false); (3) ยังไม่มีทางสร้างผู้ใช้ LOCAL — ต้องรอหน้า Admin (ขั้น 4) จึงทดลอง login จริงยังไม่ได้; (4) ตัวจำกัดอยู่ในหน่วยความจำ ถ้ารันหลายอินสแตนซ์จะนับแยกกัน

## 0d. รายชื่อผู้ใช้หน้างานชุดแรก (19 ต.ค. 2026)

ผู้ใช้ส่งรายชื่อ 13 แถว (ชื่อเล่น, ชื่อจริง, Gmail, แผนก QA & EN / QC) → ตัดสินใจ: **รหัสไล่ใหม่ตั้งแต่ F0001** · **บทบาท Admin เลือกให้ในหน้าจัดการผู้ใช้** (ไม่ใส่ตอน seed) · **ไม่ใส่บัญชีใช้ร่วม "เครื่องโรงงาน"** (Audit ระบุตัวคนไม่ได้) และไม่ใส่แถว "EN/QA" ที่ดูเป็นกล่องจดหมายกลาง → seed 11 คน F0001–F0011 ที่ `db/seed/field-users.sql` (ข้อมูลส่วนบุคคล — อยู่ใน .gitignore) · เพิ่มคอลัมน์ `nickname` ใน `users` · ทุกตาราง Master ต้องมี วันที่เพิ่ม/แก้ไข/สถานะ (+ผู้ทำ) ตาม [03 §3.0](03-spec-business-rules-data.md) · **ยังไม่ได้รันกับ DB** · ผู้ใช้เหล่านี้ยังเข้าไม่ได้จนกว่า Admin ตั้ง PIN + บทบาท (ขั้น 4)

## 0e. ความคืบหน้า — ขั้น 4 ทำแล้ว (หน้า Admin + เปลี่ยน PIN ครั้งแรก)

207 tests ผ่าน · lint/typecheck/build ผ่าน · **ทดสอบ E2E ใน Chrome แล้ว** (server แยกพอร์ต 3300, โหมด mock, store หน่วยความจำ ไม่แตะ DB จริง): Admin สร้างผู้ใช้ → ได้ F0001 + PIN ชั่วคราวแสดงครั้งเดียว → login ด้วย PIN ชั่วคราวถูกบังคับไป `/change-password` → PIN อ่อน (123456) ถูกปฏิเสธ → ตั้ง PIN ใหม่ได้ เข้า Home → F0001 เข้า `/admin/users` ได้ 404
- หน้า `/admin/users` (เมนู "ผู้ใช้หน้างาน" ในกลุ่ม "จัดการ"): รายชื่อพร้อม **วันที่เพิ่ม · วันที่แก้ไขล่าสุด · สถานะ** (ใช้งาน/ปิด, ยังไม่มี PIN, PIN ถูกล็อก, รอเปลี่ยน PIN), เข้าระบบล่าสุด · ฟอร์มเพิ่มผู้ใช้ (รหัสออกเอง), แก้ข้อมูล/บทบาท, ออก PIN ใหม่, ปลดล็อก PIN, ปิด/เปิดบัญชี
- สิทธิ์: Admin ทำได้ทั้งหมด · QC Head เข้าหน้าได้แต่ปลดล็อก PIN ของ QC Inspector ได้อย่างเดียว (I4) — ค่าประมาณ "ลูกทีมตัวเอง" เพราะยังไม่มีข้อมูลสังกัดทีม · บทบาทจำกัดที่ QC/QA Inspector ทั้งชั้น UI, logic, และตอนอ่านจาก store
- ความปลอดภัย: PIN ชั่วคราวไม่ถูกเก็บ/ล็อก (ไม่อยู่ใน audit) · การเปลี่ยน PIN ตรวจ PIN เดิมผ่านตัวจำกัดเดียวกับ login · audit ใหม่ `user.create/update/roles_change/pin_reset/pin_unlock/pin_change/deactivate/activate` (บันทึกผู้ทำ + ผู้ถูกกระทำ)
- `authenticate()` ตอนนี้จัดการรหัส `F…` ก่อนเลือกผู้ให้บริการ (ทำงานทั้งโหมด central และ mock)
- **ยังไม่ได้ทำ/ข้อจำกัด:** (1) SQL store อ่าน DB จริงได้แล้วหลังแก้ TLS และรัน repair 008 แต่ยังไม่รัน seed/ทดสอบเขียนหรือ PIN; (2) ตั้ง `PIN_PEPPER` ใน `.env.local` ของเครื่องพัฒนาแล้วด้วยค่าสุ่มที่ไม่แสดงใน log/เอกสาร; เมื่อ deploy ต้องตั้งฝั่งเซิร์ฟเวอร์และเก็บค่าเดิมไว้; (3) เปลี่ยน/ลืม PIN ของตัวเอง = ให้ Admin ออก PIN ใหม่ (ไม่มี "ลืม PIN" ด้วยตัวเอง); (4) การแก้ข้อมูล Master อื่นยังไม่ได้ทำตามมาตรฐาน §3.0 แม้มีตาราง Master ในฐานจริงแล้ว แต่ยังไม่มีหน้าจอ CRUD และยังไม่ตรวจ constraint ทุกตาราง; (5) ปุ่มสลับผู้ใช้บนเครื่องส่วนกลางยังเป็นเฟสหลัง

## 1. หลักการ: ผู้ใช้ 2 แหล่ง

| | **CENTRAL** (ออฟฟิศ — ใช้อยู่แล้ว) | **LOCAL** (หน้างาน — ใหม่) |
|---|---|---|
| ตัวตน | บัญชีระบบกลาง (`employee_no`) | สร้างใน QCheck โดย **Admin** |
| ยืนยันตัวตน | รหัสผ่านที่ระบบกลาง (API `/auth/auth_permission_prog`) | **รหัสพนักงาน + PIN** ที่ QCheck ตรวจเอง |
| บทบาท | `role_prog` ของ PRG003 (เขียนทับทุก login) | **Admin กำหนดใน QCheck** (เก็บใน `user_roles`, ไม่ถูกเขียนทับ) |
| รีเซ็ต/ปลดล็อก | ระบบกลาง (G4) | **Admin ของ QCheck** (ไม่มีระบบกลางให้พึ่ง) |
| `users.source` | `CENTRAL` | `LOCAL` |

หน้า login เดิมใช้ฟอร์มเดียว: ช่อง "รหัสพนักงาน" + ช่อง "รหัสผ่านหรือ PIN" — server ดูรหัสพนักงานก่อน: ถ้าเป็น LOCAL → ตรวจ PIN; ถ้าไม่ใช่ → ส่งระบบกลางตามเดิม · **ข้อความผิดพลาดเหมือนกัน** ("รหัสพนักงานหรือรหัสผ่านไม่ถูกต้อง") ไม่บอกว่ารหัสพนักงานนั้นเป็นชนิดไหน

## 2. ความเสี่ยงที่ต้องตัดสินใจ (อ่านก่อนอนุมัติ)

| # | ความเสี่ยง | มาตรการที่เสนอ |
|---|---|---|
| R1 | **PIN สั้นเดาง่าย** — มือถือส่วนตัวเข้าเว็บได้จากทุกที่ ไม่ใช่แค่ในโรงงาน | PIN 6 หลัก (ตั้งต้น), ห้ามเลขซ้ำ/เรียง, hash (scrypt+salt ปัจจุบัน → Argon2id เมื่อรันไทม์รองรับ) + pepper ฝั่ง server, **ผิด 5 ครั้งล็อก** ต้องให้ Admin ปลด, จำกัดต่อ IP ด้วย, แจ้งเตือน Admin เมื่อมีการล็อก |
| R2 | **ผู้ใช้ LOCAL ชนรหัสกับ CENTRAL** — ถ้า Admin สร้าง LOCAL รหัสเดียวกับพนักงานออฟฟิศ จะแย่งตัวตน/ยกระดับสิทธิ์ | รหัสพนักงาน LOCAL ใช้ **รูปแบบแยก** (เช่นขึ้นต้น `F`/`FLD`) ที่ระบบกลางไม่ใช้ · ห้ามสร้างถ้าตรงกับผู้ใช้ CENTRAL ที่มีอยู่ · `unique(employee_code)` เดียวกันทั้งสองแหล่ง |
| R3 | **บทบาทของ LOCAL เกินจำเป็น** | อนุญาตเฉพาะบทบาทปฏิบัติงานหน้างาน (ตั้งต้น: `QC_INSPECTOR`, `QA_INSPECTOR`) — **ไม่ให้** `ADMIN`, หัวหน้า, `MASTER_ADMIN` ผ่านเส้นทางนี้ · ค่าอยู่ในคอนฟิก |
| R4 | **ไม่มีผู้ปลดล็อกนอกเวลา** (Admin ลา) | บทบาท `ADMIN` ≥ 2 คน และ QC Head ปลดล็อก PIN ให้ลูกทีมได้ (เสนอ — รอยืนยัน) |
| R5 | **ผู้ใช้ที่ออกจากงาน** — ไม่มีระบบกลางปิดให้ | Admin ปิดบัญชี (`is_active = 0`) ทันที, session เดิมถูกปฏิเสธฝั่ง server ทุกคำขอ, ตรวจรายชื่อ LOCAL เป็นรอบ ๆ |
| R6 | **ล็อกอินต่อสู้กับ rate-limit เดิม** | ใช้ตัวนับเดิม (`attempts.ts`) แยกกุญแจต่อรหัสพนักงาน + ต่อ IP |

## 3. สิ่งที่ต้องสร้าง

**ข้อมูล** (migration ใหม่ `db/003_local_users.sql` — ไม่แก้ 001 ที่ถูกใช้แล้ว)
1. `users.source` รับ `LOCAL` · เพิ่ม `pin_hash`, `pin_set_at`, `pin_locked_at`, `created_by` (nullable; ใช้เฉพาะ LOCAL)
2. `user_roles` ใช้ตารางเดิม — สำหรับ LOCAL แอปไม่เขียนทับตอน login (ต่างจาก CENTRAL)
3. audit: `user.create`, `user.role_change`, `user.pin_reset`, `user.deactivate`, `login.pin_failure`, `login.pin_lockout`

**ฝั่ง server**
4. กติกา PIN (กลับมา): 4–6 หลัก (ตั้งต้น 6), ห้ามซ้ำ/เรียง, ตัวจำกัดผิด 5 ครั้งแบบล็อกจนกว่า Admin ปลด
5. hash PIN: scrypt+salt ที่มีอยู่ + pepper จาก env `PIN_PEPPER` (ไม่ต้องติดตั้งไลบรารี; Argon2id ภายหลัง)
6. ลำดับ login: หาผู้ใช้ LOCAL ตามรหัสพนักงาน → ตรวจ PIN; ไม่พบ → ระบบกลาง · session เหมือนเดิม (JWE cookie) เก็บ `source`
7. ตรวจ `is_active` ของ LOCAL ทุกคำขอ (ไม่ใช่แค่ตอน login) เพราะไม่มีระบบกลางเป็นแหล่งความจริง

**หน้าจอ**
8. หน้าจัดการผู้ใช้ (Admin, S24 ขยาย): สร้างผู้ใช้ LOCAL (ชื่อ + บทบาท + ออก PIN ชั่วคราว), รีเซ็ต/ปลดล็อก PIN, ปิด/เปิดบัญชี, ดูประวัติ
9. ผู้ใช้ LOCAL เปลี่ยน PIN ของตัวเองได้ (บังคับเปลี่ยนตอน login ครั้งแรกหลัง Admin ออก PIN ชั่วคราว)
10. หน้า login: เปลี่ยนป้ายช่องที่สองเป็น "รหัสผ่าน / PIN" + ข้อความช่วยเหลือ (อย่างสั้น)
11. เครื่องส่วนกลาง: ตัวเลือกสลับผู้ใช้ (รายชื่อที่เคยเข้าเครื่องนี้) **แยกเป็นเฟสหลัง** เพราะต้องมีทะเบียนเครื่อง (R3 ของ [10](10-pass7-shared-device-plan.md)); เฟสแรกพิมพ์รหัสพนักงาน + PIN ทุกครั้งทั้งสองแบบอุปกรณ์
12. หมดเวลาไม่ใช้งาน: ใช้ `idle.ts` เดิม (เครื่องส่วนกลาง 30 นาที / ส่วนตัว 12 ชม.)

## 5. ทางเลือกที่ควรพิจารณาก่อน

**ทางเลือก ก (ที่ออกแบบข้างบน):** QCheck มีผู้ใช้ LOCAL + PIN เอง — เร็ว, ไม่พึ่ง IT ระบบกลาง แต่ QCheck ต้องดูแลเรื่องรหัส/ล็อก/คนออกเอง

**ทางเลือก ข:** ขอ IT สร้างบัญชีระบบกลางให้พนักงานหน้างาน (รหัสพนักงาน + PRG003 `role_prog`) — ตัวตนที่เดียว, ไม่ต้องสร้างระบบจัดการรหัสเอง แต่ต้องมี "รหัสผ่าน" ไม่ใช่ PIN และขึ้นกับว่า IT ยอมสร้างและเร็วพอไหม (G8)

ผู้ใช้เลือก **ก** (PIN) ไว้แล้ว — ข้อ ข เก็บไว้เป็นทางสำรองถ้า IT ตกลงให้ ก็ย้าย LOCAL เป็น CENTRAL ได้ภายหลัง (เปลี่ยน `source` + ตั้งรหัสที่ระบบกลาง)
